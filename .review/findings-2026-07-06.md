# Deep Review — presentifyr (pass 2, 2026-07-06)

Reviewed against `.review/addendum-2026-07-06.md` (survey pass). Addendum protocol
applied: Phase-1 map spot-checked rather than rebuilt; ~80% effort on the five
priority targets; suppression list honored.

---

## 1. Architecture summary

presentifyr is an R package whose product is a single-module Shiny app that (a)
builds PowerPoint decks from R-generated figures and (b) re-syncs images and
footnotes in existing decks. Layering is consistent and thin: Shiny server
(`R/pptx_server.R`, 1229 lines, the god module) → wrapper functions
(`R/add_images.R`, `R/sync_images.R`, `R/extract_layouts.R`) that marshal config
to temp JSON → `run_python_script()` (`R/utils.R:42`) → `uv run` → Python CLIs
(`inst/scripts/*.py`) → python-pptx. The deck↔project contract is
`{prfy}:<project-relative-key>` alt-text (`prfy_image_key`, `R/utils.R:142`);
the footnote contract is reportifyr's `*_metadata.json` sidecars +
`standard_footnotes.yaml`.

**Spot-check of the survey map**: accurate. Entry points (`R/app.R:6`,
`R/initialize.R` `initialize_app`, `R/zzz.R:4`), the fan-in claims, and CI
(R-CMD-check matrix; `r-release.yaml` is a build/release pipeline, not extra
testing) all verified. Both `(?)` items confirmed: footnote font defaults are
duplicated in R (`R/pptx_server.R:16-23`) and Python
(`inst/scripts/add_images.py:266-280`) — the Python fallbacks are dormant
because the server always sends a full `font_settings`, which also means the
"plain" (unstyled) code paths in `add_images.py:402-408` are dead in app flow.
No auth/validation beyond `.pptx` extension, as claimed.

**Flows traced**: (1) generate — tree selection → preview modal
(distribute/split/merge/slot) → `downloadHandler` → `add_images()` → JSON →
`add_images.py`; (2) error path — Python `KeyError` (missing abbreviation) →
untagged traceback passes the stderr filter to the R console, but the browser
modal shows only "Add images failed. Set PRFY_VERBOSE=DEBUG for details."
(`R/utils.R:87-91`); (3) sync — upload deck → project-wide image scan → key
dict JSON → `sync_images.py` alt-text matching → MD5 gate → in-place
replace + format-preserving footnote rewrite.

**Priority-target outcomes** (details in findings):
- H1 (dead-parallel formatting): **confirmed** — zero production callers for the
  R copies; tests pin the dead copy; one behavioral drift found. Partially
  refuted on history: git shows disciplined dual edits (`5e00c73`, `843404c`
  touch both sides), i.e. the duplication tax is being paid, not skipped.
- H4 (placeholder overflow): **confirmed, worse than hypothesized** — the
  second insert into a consumed placeholder does not overlap, it *replaces*
  the earlier image via python-pptx `_replace_placeholder_with`, silently
  dropping images from the deck. Critical.
- H5 (sync key ambiguity): **confirmed** for legacy basename decks; first
  BFS-order basename match wins and can install the wrong figure.
- H2 (global paths/tempdir): **confirmed latent-High** for multi-session, and a
  concrete *single-session* thumbnail-mapping bug was found on top.
- H3 (observer registry): **largely refuted** — re-rendered action buttons
  reset to a `shinyActionButtonValue` of 0, which `observeEvent`'s
  `ignoreNULL` treats as non-truthy, so reopening the preview does not replay
  old clicks, and index-keyed observers stay semantically correct across
  reopens. The remaining kernel is real: the unguarded
  `rv$slide_positions[[slide_idx]][file_idx]` write errors on a stale index
  (verified: R raises "subscript out of bounds"), which kills the Shiny
  session (Finding 9).

**Overall read**: the R→JSON→Python layering is genuinely clean and the pure
slide algebra is well separated and tested. The structural risk is
concentrated in exactly two places: (a) domain logic duplicated across the
language boundary with tests on the wrong side, and (b) the placeholder/key
conventions that decide *which pixels land in a client deck* being enforced
nowhere (no slot-exclusivity invariant, no capacity invariant, no
basename-uniqueness invariant). All four correctness findings below are
instances of (b) producing silently-wrong decks — the failure class the
maintainers called worst.

## 2. Primary findings (ranked)

### F1. Slot collision / merge overflow silently deletes images from the generated deck
**Severity: Critical · Category: D (trust boundary / invariants) · Confidence: high**

**Evidence**
- `R/pptx_server.R:854-866` — "Merge with next" is offered whenever the slide
  has room, with no check that `len(slide) + len(next)` fits
  `placeholder_count`; `R/server_helpers.R:138-163` (`merge_slides`) happily
  produces a 3-image group with positions `1,2,3` on a 2-slot layout.
- `R/pptx_server.R:781-798, 969-972` — slot-selector buttons enforce no
  exclusivity: two images on one slide can both be assigned slot 2.
- `inst/scripts/add_images.py:360-371` — `ph_row_idx = min(max(target_pos-1,0),
  len(usable_phs)-1)` clamps both cases onto the *same* placeholder;
  `place_image_in_placeholder` (`add_images.py:123-186`) then re-fetches
  `slide.placeholders[ph_idx]` and, because the consumed placeholder is now a
  `PlaceholderPicture`, casts it back to `PicturePlaceholder` (`:148-149`) and
  calls `insert_picture` again.
- python-pptx source (verified in `pptx/shapes/placeholder.py`):
  `insert_picture` → `_replace_placeholder_with(pic)` **removes the existing
  element from the shape tree**. The cast works (`CT_Picture` inherits
  `BaseShapeElement.ph`), so no exception is raised.

**The issue.** The second image assigned to a slot does not overlap the first —
it *replaces* it. Merge a 1-image slide into a full 2-image slide on a 2-slot
layout and the deck comes out with images 1 and 3; image 2 is gone. Two images
assigned the same slot via the slot buttons: only the later one survives.
Meanwhile `slide_metadata_list` (`add_images.py:373-389`) still collects
metadata for *all* images, so the footnote block references figures that are
not on the slide. No error, no warning above DEBUG.

**Blast radius.** Silently-wrong client-facing decks — the stated worst
failure class. Reachable from two independent, ordinary UI gestures. The
mislabeled footnotes make the defect harder to catch in review, not easier.

**Remediation sketch.** Enforce the invariant at one boundary, R-side, where
the UI state lives: (a) in `merge_slides` / the merge observer, refuse (or
split) merges where `length(merged) > placeholder_count`; (b) make slot
selection exclusive (swap occupants instead of duplicating); (c) as a
belt-and-braces check, make `add_images.py` raise (not clamp) when
`len(slide_files) > len(usable_phs)` or when positions collide — the clamp at
`:362` converts a programming error into silent data loss. Effort: ~1 day
including tests.

### F2. Sync's basename fallback can silently install the wrong figure in an existing deck
**Severity: High · Category: D (serialization contract drift) · Confidence: high (mechanism); medium (frequency)**

**Evidence**
- `inst/scripts/sync_images.py:314-324` — on exact-key miss, falls back to the
  *first* dict entry whose basename matches:
  `if os.path.basename(key) == figure_name or os.path.basename(path) == figure_name`.
- `R/sync_images.R:37-40` — dict keys are project-relative paths from
  `parse_directory_for_images` BFS order (`R/utils.R:187-222`); `keys_legacy`
  (`:38`) is computed and never used, so basename keys are *only* resolvable
  via the Python fallback.
- `inst/scripts/sync_images.py:344-352` — the matched file then replaces the
  deck image and (`:357-406`) rewrites its footnotes from that file's metadata.

**The issue.** Legacy decks carry `{prfy}:<basename>` alt-text. Projects
realistically contain duplicate basenames across run directories
(`run1/dv_pred.png`, `run2/dv_pred.png`). The fallback picks whichever
subdirectory the BFS scan visits first — a property of directory naming, not
of the deck. Hashes then differ ("content changed"), so the wrong figure is
installed *and* its footnotes are rewritten to match the wrong source, with an
INFO log as the only trace.

**Blast radius.** A re-synced review deck can show run-A figures on slides
that documented run-B, with internally consistent (wrong) footnotes.
Undetectable from inside the deck.

**Remediation sketch.** Make ambiguity a hard error: collect *all* basename
matches; if >1, raise listing the candidates (the R side already has the full
scan to display them). Optionally emit a one-time WARNING when the fallback is
used at all, nudging users to regenerate decks with relative keys. Delete
`keys_legacy`. Effort: ~2-4 hours.

### F3. Footnote formatting exists twice (R + Python); the tests pin the dead copy, and drift has already begun
**Severity: High · Category: A (duplicated domain concept) / E (tests anti-correlated with risk) · Confidence: high**

**Evidence**
- Dead copies: `format_slide_notes`, `format_source_line`,
  `decode_abbreviations`, `load_image_metadata` (`R/utils.R:335-529`) have
  **zero production callers** — grep across `R/` finds only their definitions;
  all callers are in `tests/testthat/test-format_slide_notes.R` and
  `test-load_image_metadata.R` (~30 of the ~90 tests).
- Live copies: `inst/scripts/pptx_utils.py:29-219`, called by both
  `add_images.py:387` and `sync_images.py:370` — and covered by no tests at all.
- Existing drift: R strips *one* trailing period from abbreviation full-forms
  (`sub("\\.$", "", full_form)`, `R/utils.R:526`) while Python strips *all*
  (`rstrip('.')`, `pptx_utils.py:92`).
- History (partial refutation of the survey hypothesis): `5e00c73` and
  `843404c` edited R, Python, and the R tests together — maintainers are
  paying the synchronized-edit tax, not skipping it. Nothing enforces it.

**The issue.** This is the out-of-repo reportifyr contract, implemented twice
with no mechanism keeping the copies aligned. The test suite creates false
confidence: a green run certifies text that never reaches a deck, while the
string that lands in client decks is exercised only in production. Every
contract change costs three synchronized edits (R, Python, R tests), and the
one behavioral divergence that exists is on the untested side.

**Blast radius.** Change amplification on every footnote-contract change;
a silent formatting regression in `pptx_utils.py` would ship with all tests
green.

**Remediation sketch.** Pick one owner — Python is the natural one since it
holds the deck. Delete the four R functions and their tests; port the test
matrix to pytest against `pptx_utils.py` (stdlib-only, trivially testable) and
run it in CI via `uv run pytest`. If the R copies are being kept deliberately
as executable documentation of the reportifyr contract, add a cross-language
golden test (same metadata JSON through both, diff output) so drift fails CI.
Effort: ~1-2 days including CI wiring.

### F4. Two same-basename images on one slide: one image's footnotes are silently dropped/mislabeled
**Severity: High · Category: B (partial failure, silent) · Confidence: high**

**Evidence**
- `inst/scripts/add_images.py:374-376` —
  `slide_metadata_list[os.path.basename(file_path)] = metadata`: a dict keyed
  by basename; the second image overwrites the first.
- `inst/scripts/sync_images.py:360-364` — identical pattern on the sync path.
- The combined notes emit one `## <basename>` block per key
  (`add_images.py:383-389`, `sync_images.py:368-372`).

**The issue.** Placing `run1/dv_pred.png` and `run2/dv_pred.png` side by side
on one comparison slide — a bread-and-butter pharmacometrics use — produces a
slide with both images but only *one* footnote block, labeled with the shared
basename, containing whichever image's Source/Notes/Abbreviations happened to
be processed last. A reviewer cannot tell one source attribution is missing
and the other is unattributable to a specific panel. (Related: the block
headers in decks are basenames, so `update_text_preserve_formatting`'s
header-keyed matching (`sync_images.py:155-259`) would also cross-match blocks
if duplicates ever did coexist — lxml `append` *moves* elements, corrupting
the earlier block.)

**Blast radius.** Wrong/incomplete source attribution in client decks,
precisely on comparison slides. Silent.

**Remediation sketch.** Key `slide_metadata_list` by the prfy key (relative
path) instead of basename in both scripts, and use the key (or a disambiguated
name) in the `##` header. Note this changes the sync block-matching key for
existing decks — handle by matching header text against both old basename and
new key form for one transition period. Effort: ~half a day.

### F5. Sync stretches replacement images into the old shape's bounds — aspect-ratio distortion
**Severity: Medium · Category: D · Confidence: high (mechanism); medium (that it's unintended)**

**Evidence**
- `inst/scripts/sync_images.py:344-352` — replacement reuses the old shape's
  `left/top/width/height` verbatim: `add_picture(image_path, left, top, width, height)`.
- Generation, by contrast, letterboxes to the image's aspect ratio inside the
  placeholder (`inst/scripts/add_images.py:160-180`).

**The issue.** The old shape's rect encodes the *old* image's aspect ratio.
Regenerate a figure with different dimensions (added panel, changed device
size — routine between review rounds) and sync draws the new pixels stretched
into the old rect. No warning; the hash gate guarantees this fires exactly
when the figure changed.

**Blast radius.** Distorted figures in re-synced client decks. Subtle
distortions (5-10%) are the dangerous ones — enough to misrender a plot,
not enough to be obvious.

**Remediation sketch.** Compare old-rect aspect to new-image aspect; when they
differ beyond a tolerance, aspect-fit the new image within the old rect
(centered), preserving user repositioning while never distorting. ~2-4 hours.
If exact-rect reuse is intentional (respect user resizes), log a WARNING on
aspect mismatch at minimum.

### F6. Application-global resource paths + shared tempdir: wrong/broken thumbnails within a session today, cross-session clobbering when server-deployed
**Severity: Medium (latent High under multi-session) · Category: C (lifecycle/shared state) · Confidence: high**

**Evidence**
- `R/pptx_server.R:618-626` and `:1144-1150` — `preview_imgs_<i>` /
  `filelist_imgs_<i>` registered only if the *name* is absent, but the name is
  positional (`i`) while the directory it should map to changes per
  preview/render.
- `R/pptx_server.R:739-749` — `get_image_web_path` resolves `i` against the
  *current* `rv$img_dirs`, not against what the name was registered to.
- `R/pptx_server.R:429-443` — every template upload wipes and reuses the
  process-wide `tempdir()/prfy_layouts` and re-points the global
  `pptx_layouts` resource path.
- `R/pptx_server.R:1200-1219` — *any* session ending removes the shared layout
  dir and **all** `preview_imgs_*`/`filelist_imgs_*` paths process-wide.
- `R/zzz.R:5` — `addResourcePath("presentifyr", system.file(".", ...))` serves
  the entire installed package directory over HTTP.

**The issue (single session, today).** Preview figures from `model1/`, cancel,
then preview figures from `model2/`: `preview_imgs_1` is already registered →
registration skipped → still maps to `model1/`, while `rv$img_dirs[1]` is now
`model2/`. Thumbnails 404 — or worse, with pharmacometrics' recurring
basenames, *show model1's figure while the deck will contain model2's*. The
preview exists to let the user verify arrangement; it can display the wrong
images. Same drift applies to `filelist_imgs_*` as selections change.

**The issue (multi-session, latent).** Resource paths and `tempdir()` are
process-global: concurrent sessions cross-serve each other's directories,
template uploads destroy each other's layout carousels, and one session's end
breaks every other session's thumbnails. Per the addendum this is rated latent
rather than Critical (local single-user today), but note the single-session
bug above fires *now*. The package-root resource path additionally exposes all
R sources/scripts to any browser that can reach the port.

**Remediation sketch.** One namespaced prefix per session
(`paste0("imgs_", session$token, "_", i)`), registered fresh per preview and
removed on modal close/session end; key the dir→name mapping in a session-local
env instead of positional index; move layouts to
`file.path(tempdir(), paste0("prfy_layouts_", session$token))`; scope `zzz.R`
to `system.file("www", ...)` + the JS/CSS files actually referenced. Effort:
~1 day.

### F7. Actionable Python errors reach the R console but not the user: generic modal at the boundary
**Severity: Medium · Category: B (error-context loss) · Confidence: high**

**Evidence**
- `R/utils.R:87-91` — every Python failure is replaced by
  `"<label> failed. Set PRFY_VERBOSE=DEBUG for details."`.
- The messages being discarded are user-actionable by design:
  `pptx_utils.py:88-91` ("Abbreviation 'X' not found in abbreviations section
  of footnotes YAML"), `:171-175` (meta_type missing),
  `add_images.py:55` ("Invalid layout name ... not found in template"),
  `:313` ("No usable placeholder found").
- The modal wrappers (`R/pptx_server.R:578-581`, `:1021-1023`, `:445-448`)
  faithfully display the already-genericized message.

**The issue.** The Python layer was carefully written to tell the user exactly
which YAML key to add or which layout doesn't exist, and R's `[LEVEL]`-tag
filter already lets untagged tracebacks through to the *console* — but the
user is in a browser looking at a modal. The DEBUG hint is doubly misleading:
the traceback prints regardless of `PRFY_VERBOSE`, and re-running with an env
var requires restarting the app. Every realistic failure (missing YAML key,
bad layout, corrupt template, missing venv) presents identically.

**Blast radius.** Support burden and user dead-ends on the most common
failure mode of the reportifyr contract (footnotes YAML incomplete).

**Remediation sketch.** Have the stderr callback capture the last
`ValueError:/KeyError:` line (or teach the Python CLIs to `sys.exit(str(e))`
so the message rides the process error), and append it to the re-raised R
error: `stop(label, " failed: ", captured_detail)`. The modal plumbing needs
no change. ~2-4 hours.

### F8. tree.js: two in-flight folder loads race on one global `Children` — children can attach to the wrong folder
**Severity: Medium · Category: C (concurrency) · Confidence: medium**

**Evidence**
- `inst/tree.js:4-14` — a single global `Children`/`childrenFlag` pair,
  overwritten by every `getChildren` message.
- `inst/tree.js:79-115` — each folder click starts its *own* 100 ms
  `setInterval` that consumes whichever `Children` is non-null and creates the
  nodes under its own captured `id`.
- Server side sends no correlation id: `R/treeNav.R:182-188`.

**The issue.** Click folder A, then folder B before A's response arrives (one
Shiny round trip; easy on network storage where `list_files_and_dirs` also
stats every entry, `R/treeNav.R:59-65`). Two intervals now poll one mailbox.
A's response can be consumed by B's interval, mis-parenting the listing.
Since node paths feed `treeNavigator_selected_paths` → `rv$pending_files` →
the generated deck, a mis-parented listing lets a user select a path that
doesn't exist or isn't the file shown. Also: if the server observer errors
(neither `getChildren` nor `noChildrenFound` sent), the interval polls forever
— an unbounded 100 ms timer per failed click.

**Blast radius.** Wrong tree contents / dead-end selections under normal
impatient clicking; degrades with project size and FS latency.

**Remediation sketch.** Include the requested path in both the input and the
`getChildren` payload; key the pending state by path (or per-node), have each
interval consume only its own key, and add a timeout that clears the interval.
~2-4 hours, JS + one R line.

### F9. Preview slot observers write through stale indices — an out-of-bounds write kills the session
**Severity: Medium · Category: C · Confidence: medium**

**Evidence**
- `R/pptx_server.R:969-972` — `rv$slide_positions[[slide_idx]][file_idx] <- pos`
  with no bounds guard; observers for every `(s, f, p)` ever rendered live for
  the whole session (`.created_obs`, `:883-979`) and are never destroyed.
- Verified semantics: for `length(x) == 2`, `x[[3]][1] <- 5` raises
  "subscript out of bounds"; an uncaught observer error terminates the Shiny
  session.

**The issue.** The survey's replay hypothesis is refuted (see architecture
summary): re-rendered action buttons reset to a non-truthy 0, so reopening the
preview does not re-fire old observers. But two clicks queued within one
round-trip — e.g. "Merge with next" (slides 3→2) followed immediately by a
`pos_3_*` click on the not-yet-re-rendered UI — deliver the second event to an
observer whose `slide_idx` no longer exists. The write throws, the session
dies, and the user loses template, layout, and arrangement state. The
same-shape hazard exists for `merge_slide_`/`split_before_` but those handlers
happen to bounds-check (`:942`; split indices stay valid).

**Blast radius.** Full-session crash from fast clicking in the arrangement
modal; low frequency, high annoyance, zero data corruption.

**Remediation sketch.** Guard the handler:
`if (slide_idx > length(rv$slide_positions) || file_idx > length(rv$slide_positions[[slide_idx]])) return()`.
Longer term, replace the three hand-rolled observer registries with a single
delegated input (`Shiny.setInputValue("slot_click", {s,f,p}, {priority:"event"})`)
so there is one observer and no registry. Guard: minutes; refactor: ~half a day.

### F10. Test architecture is anti-correlated with risk: the deck-producing code has zero tests
**Severity: Medium · Category: E · Confidence: high**

**Evidence**
- ~1,700 lines of testthat across 22 files cover pure R helpers — including
  the ~30 tests on the dead formatting copies (F3) and thorough coverage of
  `server_helpers.R`.
- Zero tests: all three Python scripts (the only code that touches .pptx
  bytes), `pptx_server.R`'s reactive logic, `treeNav.R`'s server, and the
  R↔Python JSON contract (`test-add_images.R`/`test-sync_images.R` mock
  `run_python_script` and assert only that args are passed).

**The issue.** Every finding above (F1, F2, F4, F5) lives in the untested
layer; none could be caught by the current suite. The suite's shape actively
misleads: contract changes appear covered because the R mirror is tested.

**Blast radius.** Regressions in generated/synced deck content ship silently;
this compounds every other finding.

**Remediation sketch.** Highest-value additions, in order: (1) pytest
golden-file tests for `add_images.py` — build a deck from a fixture config,
re-open with python-pptx, assert image count per slide, alt-text keys, and
notes text (immediately locks in F1's fix); (2) pytest for
`sync_images.py` matching + `update_text_preserve_formatting` on a fixture
deck (locks F2/F4); (3) port the formatting matrix to `pptx_utils.py` (F3).
Run via `uv run pytest` in the existing CI. Effort: ~2-3 days for the initial
harness; each subsequent test is cheap.

## 3. Low-hanging fruit

- `R/sync_images.R:38` — `keys_legacy` computed, never used. Delete (or use it:
  see F2).
- `R/treeNav.R:55` — `grepl(pattern, included_files)` lacks `ignore.case = TRUE`,
  so `PLOT.PNG` is invisible in the tree while `parse_directory_for_images`
  (`R/utils.R:186,206`) matches it case-insensitively — the two image-discovery
  implementations disagree. Add the flag.
- `R/treeNav.R` — the tree applies no `default_exclude_dirs()`; users can
  browse into `rv/library`, `renv`, `.git` and select vendored images that the
  sync scan would deliberately skip. Filter dirs in `list_files_and_dirs`.
- `R/pptx_server.R:1024-1028` — `finally = { on.exit({...}) }` registers the
  cleanup on tryCatch's internal frame; just put the `file.remove` directly in
  `finally`.
- `R/utils.R:58` — `r_levels[[Sys.getenv("PRFY_VERBOSE", unset = "WARN")]]`
  crashes with bare "subscript out of bounds" if the env var is set to an
  invalid value after package load (load-time validation in `toggle_logger`
  doesn't protect later changes). Validate with a default.
- `inst/scripts/extract_layouts.py:35,60,95` — `safe_layout_name` collisions
  ("Title Slide" vs "Title_Slide") silently overwrite both the PNG and the
  metadata entry; add a uniquifying suffix. Relatedly `R/extract_layouts.R:51`
  re-sorts layouts alphabetically, so carousel order ≠ template order.
- `inst/scripts/sync_images.py:316` — `match.group(0).split(':')[1]` truncates
  keys containing `:` (legal in POSIX filenames); use `split(':', 1)[1]`.
- `inst/scripts/sync_images.py:82` — `slide.notes_slide` in
  `should_update_notes` *creates* a notes slide part as a side effect even
  when the comparison says "skip", so "unchanged" decks still gain empty notes
  parts. Check `slide.has_notes_slide` first.
- `R/server_helpers.R:19` — `regroup_files` mis-indexes (`files[1:0]`) if any
  group is empty; unreachable through today's UI (split button hidden for
  `file_idx == 1`, `R/pptx_server.R:779`) but a one-line `if (sizes[i] == 0)`
  guard removes the trap.

## 4. Questions for maintainers

1. **Sync vs. user edits to footnotes**: `update_text_preserve_formatting`
   deliberately re-inserts lines the user deleted (`sync_images.py:260-265`)
   and drops paragraphs the user added, and the rewrite triggers whenever the
   footer differs from canonical — even when no image changed. Is "footnotes
   are always regenerated from metadata" the intended contract? If yes, a line
   in the README would prevent surprise; if no, this is a finding.
2. **GROUP shapes** (`sync_images.py:305-306`): `shape.image.blob` raises for
   groups, so `should_replace_image` always answers "replace" — every sync
   replaces a matched group with a flat picture (dropping other group
   members), and the operation is non-idempotent. When do prfy-tagged groups
   actually occur? If never, drop the branch; if they do, this needs its own
   handling.
3. **Slot assignments reset on any reorder** — `regroup_files`/`merge_slides`/
   `split_before_index` all reset positions to sequential, discarding explicit
   slot choices anywhere in the deck after any up/down click. Intended?
4. **Template uploaded but no layout selected**: `chosen_layout` is NULL, so
   Python defaults to `prs.slide_layouts[1]` *of the user's template*
   (`add_images.py:40-44`) — an arbitrary layout that may have no usable
   placeholders (→ opaque error via F7). Should the UI require a layout
   selection once a template exists?

## 5. What's good (preserve these)

- **The R→JSON→Python CLI boundary is disciplined.** Every wrapper follows the
  same shape (marshal config → temp JSON → `run_python_script`), compat
  shaping stays R-side by stated policy, and the `[LEVEL]`-tag logging bridge
