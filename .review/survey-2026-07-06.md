## 1. Repository map

**Purpose.** presentifyr is an R package (v0.3.1, GPL-3, by A2-ai) whose sole
deliverable is a Shiny application that builds and re-syncs PowerPoint decks
from R-generated figures. Users pick images from a project file tree, arrange
them onto slides using layouts extracted from an uploaded .pptx template, and
download a generated deck; a companion "sync" flow updates images/footnotes in
an existing deck in place. All actual .pptx manipulation is done by Python
(python-pptx + Pillow) subprocesses run via `uv` in a pyro-managed venv.

**Codebase type.** Hybrid: R package + Shiny web app (single-module) +
bundled Python CLI scripts + a small amount of bundled JS/CSS. Exported R API
is tiny: `app()`, `initialize_app()`, `get_project_dir()`, `toggle_logger()`.

**Entry points.**
- `R/app.R:6` — `app()`: builds and runs the Shiny app (`app_ui` in
  `R/pptx_ui.R:42`, `app_server` in `R/pptx_server.R:1225`).
- `R/initialize.R:30` — `initialize_app()`: bootstraps the Python venv via
  `pyro::initialize_python(groups = "presentifyr")`.
- `R/zzz.R:4` — `.onLoad`: registers a package-wide Shiny resource path,
  sets `options(shiny.maxRequestSize = 5GB)`, initializes the logger.
- Python CLIs (invoked as subprocesses, each with `argparse` mains):
  `inst/scripts/add_images.py`, `inst/scripts/sync_images.py`,
  `inst/scripts/extract_layouts.py`.

**Module inventory.**
| Path | Responsibility | Size | Notable deps |
|---|---|---|---|
| `R/pptx_server.R` | The entire Shiny server: config modal, template upload/layout carousel, slide-arrangement preview (move/split/merge/slot), sync flow, download handlers, session cleanup | 1229 lines — the god module | shiny, htmltools, log4r; calls every other R file |
| `R/server_helpers.R` | Pure slide-grouping algebra: `regroup_files`, `split_before_index`, `distribute_files_to_slides`, `merge_slides`, `sanitize_filename` | 164 lines | none (pure) |

**Intended layering** (inferred from the thin-wrapper pattern and roxygen
comments): Shiny server → R wrapper functions (`add_images`, `sync_images`,
`extract_layouts`) → `run_python_script` (`R/utils.R:42`) → `uv run` Python
CLI → python-pptx. Contract between R and Python is JSON temp files plus CLI
flags; contract between decks and sync is the `{prfy}:<key>` alt-text
convention where `<key>` comes from `prfy_image_key()` (`R/utils.R:142`).
Metadata flows in from a sibling package (reportifyr) via `*_metadata.json`
sidecars and `<report_dir>/standard_footnotes.yaml`; several docstrings say
"mirrors reportifyr's" behavior — an out-of-repo convention contract.

**Most load-bearing files.**
1. `R/pptx_server.R` — every user interaction routes through it (highest
   fan-in for R helpers, all UI state lives in its `reactiveValues`).
2. `inst/scripts/pptx_utils.py` — imported by all three Python CLIs; owns the
   footnote-formatting contract shared with reportifyr.
3. `R/utils.R` — `run_python_script`, `get_project_dir`, `prfy_image_key` sit
   on every command path.

**Cross-cutting concerns.**
- *Errors*: R side uses `stop()` + `tryCatch` in server observers →
  `show_error_modal` (`R/utils.R:100`). `run_python_script` (`R/utils.R:78-91`)
  catches all Python failures and replaces the message with a generic
  "`<label>` failed. Set PRFY_VERBOSE=DEBUG for details." Python raises
  `ValueError`/`KeyError` freely; tracebacks reach R only via a stderr
  callback that filters by `[LEVEL]` tag (untagged lines always pass).
- *Logging*: log4r logger in package env `.le` (`R/toggle_logger.R:1`),
  level from env var `PRFY_VERBOSE`; Python emits everything to stderr at
  DEBUG (`inst/scripts/py_logger.py`) and R filters (`R/utils.R:52-76`).
- *Config*: three R options (`project.dir`, `presentifyr.exclude_dirs`,
  `presentifyr.report_dir_name`) + env vars `PRFY_VERBOSE`,
  `PRFY_EXCLUDE_DIRS`; precedence logic in `default_exclude_dirs()`
  (`R/utils.R:115`). Footnote font defaults exist in both R
  (`R/pptx_server.R:16-23`) and Python (`add_images.py:_apply_font_settings`
  fallbacks) (?).
- *Auth/validation*: none (local single-user app assumed (?)); file inputs
  validated only by `.pptx` extension (`validate_pptx_file`, `R/utils.R:20`).
- *Concurrency*: none explicit. Shared global state exists: Shiny resource
  paths are application-global (`pptx_layouts`, `preview_imgs_*`,
  `filelist_imgs_*`), and `tempdir()/prfy_layouts` is shared per R process.
- *Resource lifecycle*: `session$onSessionEnded` (`R/pptx_server.R:1200`)
  removes the layout dir and **all** dynamic resource paths.

**Build/test/CI.** Standard R package built with roxygen2; deps pinned via
`rv` (`rproject.toml`, internal PRISM/pyro repositories); docs via starlightr.
CI: GitHub Actions R-CMD-check matrix (macOS/Windows/Ubuntu, R 4.3–4.5) plus a
large `r-release.yaml` (not read closely) (?). testthat (edition 3, ~90 tests)
covers small pure R helpers with `mockery` for the Python boundary; **there
are no tests for `pptx_server.R` reactive logic, none for `treeNav.R`'s
server, and no Python tests at all.**

## 2. Risk hypotheses (ranked, max 8)

### H1 — The R footnote-formatting layer is a dead parallel implementation of the Python one, and the two have no drift guard
- **Hypothesis**: `format_slide_notes`, `format_source_line`,
  `decode_abbreviations`, and `load_image_metadata` in `R/utils.R:335-529`
  have zero production callers — the runtime path serializes definitions to
  JSON and lets `inst/scripts/pptx_utils.py:97-219` do the formatting — yet
  the R copies are the ones with the most tests, so test effort validates
  code that never runs, while the code that runs is untested and can drift.
- **Signal**: `grep` for callers of these four functions outside `utils.R`
  finds only `tests/testthat/test-format_slide_notes.R` (19 tests) and
  siblings. Both implementations carry twinned comments ("Right-trim before
  checking trailing period…" at `R/utils.R:458` and
  `pptx_utils.py:178`), i.e. they are maintained by hand in lockstep.
- **If true, cost**: silent behavioral divergence between what tests assert
  and what decks contain; every footnote change must be made twice; sync's
  hash comparison (`sync_images.py:61-99`) regenerates text Python-side, so
  R-side drift wouldn't even be observable — just misleading.
- **Investigation sketch**: confirm call graph (grep callers of each);
  diff the two implementations line-by-line for existing behavioral drift
  (e.g. R `decode_abbreviations` uses `sub("\\.$", "", x)` vs Python
  `rstrip('.')` — differ on multiple trailing dots); decide dead-code vs
  spec role; check git log for changes applied to one side only.
- **Confidence**: high.

### H2 — Application-global resource paths and a shared temp dir break under concurrent sessions
- **Hypothesis**: the app registers Shiny resource paths and writes to fixed
  `tempdir()` locations that are global to the R process, so two concurrent
  sessions corrupt each other's layout previews and thumbnails, and a session
  ending destroys resources other live sessions still reference.
- **Signal**: `shiny::addResourcePath("pptx_layouts", output_dir)` at
  `R/pptx_server.R:439` with fixed dir `tempdir()/prfy_layouts` (created at
  `:429`, cleared at `:432`, deleted on any session end at `:1200-1209`);
  `preview_imgs_<i>`/`filelist_imgs_<i>` registered only "if not already
  present" (`:622-625`, `:1145-1150`) so a second session silently inherits
  the first session's directory mapping; session cleanup removes **all**
  `preview_imgs_*`/`filelist_imgs_*` paths (`:1212-1216`), not just its own.
  Also: registering these paths serves entire directories over HTTP, and
  `.onLoad` (`R/zzz.R:5`) serves the whole installed package root.
- **If true, cost**: for any multi-user deployment (Posit Connect / Shiny
  Server), wrong thumbnails, broken previews, cross-user file exposure, and
  layouts vanishing mid-flow. If the app is strictly local single-user
  [Q2], cost drops to latent deployment hazard.
- **Investigation sketch**: enumerate all `addResourcePath`/`resourcePaths`/
  `tempdir()` call sites in `pptx_server.R`; simulate two sessions'
  interleaving on paper (A previews, B previews, A ends); check whether
  `session$token` or per-session tempdirs are used anywhere (they aren't, at
  first read).
- **Confidence**: high (mechanism certain; severity hinges on [Q2]).

### H3 — The dynamically-created-observer registry leaks observers and can fire ghost events across preview reopens
- **Hypothesis**: `pptx_server.R` creates `observeEvent`s in loops keyed by
  global file index / slide index / slot triple, records them in `.created_obs`
  (`R/pptx_server.R:883-979`), and never destroys them; because rendered
  buttons reuse the same input IDs across preview modal reopens with different
  file sets, stale observers outlive their UI and re-rendered buttons can
  replay or misroute clicks.
- **Signal**: `.created_obs$move`/`$merge`/`$pos` only ever grow; observers
  capture `idx` but read `rv$slide_groups` at fire time; `input$pos_2_1_3`
  from a previous arrangement session refers to a different image now;
  nothing calls `destroy()` on any observer; the preview modal can be opened
  repeatedly per session with different selections.
- **If true, cost**: user-visible misbehavior that is hard to reproduce
  (wrong image moves after reopening preview; slot assignments applied to the
  wrong slide), plus unbounded per-session observer growth (minor memory).
- **Investigation sketch**: trace one concrete replay: open preview with 4
  files → split → close → reselect 2 files → open preview; enumerate which
  `pos_s_f_p` and `move_up_N` IDs get rendered and which old observers still
  listen; check Shiny semantics for re-rendered `actionButton` values
  (re-render resets value to 0 — with `ignoreInit = TRUE` on the *first*
  registration only, does the reset trigger?); look for guards clamping
  `idx`/`slide_idx` at fire time (some exist, e.g. `:942`, some don't, e.g.
  `pos_` handler at `:969-972` writes `rv$slide_positions[[slide_idx]][file_idx]`
  unguarded).
- **Confidence**: medium (pattern is certainly fragile; whether a concrete
  user-reachable misfire exists needs the trace).

### H4 — Merge/slot UI can exceed placeholder capacity and Python's silent clamping stacks images on top of each other
- **Hypothesis**: `merge_slides` can produce a slide with more images than the
  layout has placeholders (merge is offered whenever the slide has room and
  isn't last: 1 image + 2-image next slide on a 2-slot layout ⇒ 3 images),
  and the slot selector lets two images choose the same slot; Python then
  clamps `target_pos` into range (`add_images.py:362`:
  `min(max(target_pos-1,0), len(usable_phs)-1)`) and inserts multiple images
  into the same placeholder without warning.
- **Signal**: merge button condition `slide_has_room && slide_idx < length(...)`
  at `R/pptx_server.R:856` bounds merged size only by `2*ph_count - 1`;
  position buttons (`:783-798`) render per-image with no cross-image
  exclusivity; the clamp line in `add_images.py:362`; inserting into an
  already-consumed placeholder goes through the
  `PicturePlaceholder(ph._element, ...)` cast path (`add_images.py:148-152`)
  whose behavior on a consumed placeholder is untested.
- **If true, cost**: silently wrong decks — overlapping or vanished images —
  in the tool's core "generate" flow; users may ship the deck without
  noticing.
- **Investigation sketch**: construct the 1+2-on-2-slots merge on paper from
  `merge_slides` (`R/server_helpers.R:138`) and follow the groups/positions
  JSON into `add_images.py`; determine what python-pptx does when
  `insert_picture` targets an idx that was already consumed; check whether
  any R-side validation exists between preview state and `add_images()` call
  (`R/pptx_server.R:1002-1010`).
- **Confidence**: medium-high.

### H5 — Sync's image-key matching is ambiguous under duplicate basenames and half its backward-compat machinery is dead
- **Hypothesis**: the `{prfy}:<key>` → file resolution silently picks an
  arbitrary file when basenames collide, and the R side builds (but never
  uses) a legacy key vector, so the intended backward compatibility exists
  only as a Python-side linear scan with first-match-wins semantics.
- **Signal**: `keys_legacy <- basename(image_files)` at `R/sync_images.R:38`
  is never referenced again; `image_dict` is keyed only by
  relative-path keys (`:40`), and `stats::setNames` silently deduplicates
  collisions (last (?) one wins) e.g. when files fall back to basename keys;
  Python fallback loop `sync_images.py:319-324` breaks on the first entry
  whose basename matches. `prfy_image_key` itself falls back to bare
  basename for outside-root files (`R/utils.R:148`).
- **If true, cost**: sync replaces a figure with the wrong same-named file
  (e.g. `model1/ofv.png` vs `model2/ofv.png`) — a silent correctness failure
  in a pharma reporting context; dead code misleads maintainers about what
  compat exists.
- **Investigation sketch**: build the collision case (two `plot.png` in
  different dirs, deck created pre-0.3 with basename alt-text); trace dict
  construction in `R/sync_images.R:37-45` and lookup in
  `sync_images.py:314-341`; check ordering guarantees of
  `parse_directory_for_images` BFS (`R/utils.R:187-222`) that determine which
  file wins; confirm `keys_legacy` is dead.
- **Confidence**: medium-high.

### H6 — Test coverage is anti-correlated with risk across all three languages
- **Hypothesis**: the ~90 R tests exercise small pure helpers (several of
  them the dead H1 functions), while the actual risk concentrations — the
  1229-line reactive server, the format-preserving paragraph rewriter, and
  everything Python — have zero tests.
- **Signal**: test file list covers only `utils.R`/`server_helpers.R`/
  `treeNav.R` helpers + wrapper arg-marshaling with mocked Python
  (`tests/testthat/helper.R`); no `shiny::testServer` usage; no Python test
  directory; `sync_images.py:133-265` (`update_text_preserve_formatting`,
  the subtlest algorithm in the repo — block/key paragraph matching with
  formatting reuse) is untested and unreachable from any R test because
  mocks cut the boundary.
- **If true, cost**: regressions in the flows users actually run (arrange,
  generate, sync) ship undetected; refactoring the server module is
  effectively frozen.
- **Investigation sketch**: map each test file to the module it covers and
  produce the coverage-vs-risk table; identify the 3–4 highest-value missing
  test targets (e.g. golden-file pptx round-trip driven from Python directly,
  `testServer` for preview state machine).
- **Confidence**: high (the gap is a fact; Pass 2 should size the risk, per
  base-prompt Category E).

### H7 — Error context is destroyed exactly at the boundary users hit most
- **Hypothesis**: every Python failure surfaces to the UI as
  "`<label>` failed. Set PRFY_VERBOSE=DEBUG for details." while the
  underlying cause (missing abbreviation key, bad layout name, corrupt pptx)
  was a precise, user-actionable message; meanwhile deliberate Python-side
  `raise ValueError/KeyError` messages are written for humans who will never
  see them at default verbosity.
- **Signal**: `run_python_script`'s catch-all at `R/utils.R:87-91` discards
  `e$message` content; `find_layout_by_name` raises a precise ValueError
  (`add_images.py:55`); `decode_abbreviations` raises KeyError with guidance
  (`pptx_utils.py:88-91`); the stderr callback shows `[ERROR]`-tagged lines
  at default WARN threshold (`R/utils.R:58`) — but only on the R console, not
  in the modal the user is looking at.
- **If true, cost**: support burden and user dead-ends in the app's most
  common failure modes (missing footnote YAML entries, wrong template).
- **Investigation sketch**: trace one failure end-to-end (unknown
  abbreviation key during generate): Python raise → pyro error → tryCatch →
  modal text; inventory which failure classes produce actionable modals vs
  the generic one; check whether pyro's error object carries stderr that
  could be forwarded (`R/initialize.R:48-50` shows it sometimes does).
- **Confidence**: medium.

### H8 — The jstree lazy-load glue's global mutable state races on fast clicks
- **Hypothesis**: `inst/tree.js` coordinates folder expansion through
  process-global variables (`Children`, `childrenFlag`) and a 100 ms
  `setInterval` poll; two quick clicks on different folders interleave and
  attach children to the wrong node or lose a response.
- **Signal**: globals at `inst/tree.js:4-8`; poll loop `:79-115`; the
  handler stores per-click state in shared vars with no request identity;
  R side answers via a single `getChildren` custom message with no
  correlation id (`R/treeNav.R:188`).
- **If true, cost**: misplaced tree nodes / stuck spinner; low blast radius
  (refresh fixes it), but it's on the primary selection path.
- **Investigation sketch**: simulate two overlapping `path_from_js` events;
  check whether Shiny input debouncing serializes them in practice; assess
  whether jstree's own loading callback could replace the poll.
- **Confidence**: low-medium.

## 3. Questions for the maintainer (max 10)

Each with the default Pass 2 will assume if unanswered.

- **Q1 → H1**: The R implementations of `format_slide_notes` /
  `format_source_line` / `decode_abbreviations` / `load_image_metadata`
  (`R/utils.R:335-529`) appear to have no production callers — Python does the
  runtime formatting. Are they (a) leftovers from the pre-Python era, (b) a
  deliberate tested "spec" for the Python code, or (c) used by something
  outside this repo? **Default: (a) leftovers — review as dead duplicate
  implementations that can drift.**
- **Q2 → H2**: Is presentifyr strictly a locally-run, one-user-per-R-process
  app, or is deployment on a multi-session server (Posit Connect / Shiny
  Server) supported or planned? **Default: local single-user today, server
  deployment plausible later — cross-session issues rated High-latent, not
  Critical.**
- **Q3 → H4**: When a user merges slides or picks slots such that images
  exceed/collide on placeholders, is silent clamping (images stacked in the
  last/same placeholder) known and accepted, or should the UI prevent it?
  **Default: not accepted — treat silent overlap as a bug.**
- **Q4 → H7**: Is the generic "X failed. Set PRFY_VERBOSE=DEBUG" modal a
  deliberate choice to hide tracebacks from end users (pharma-scientist
  audience), or just the current state? **Default: deliberate for tracebacks,
  but actionable causes (missing YAML key, bad layout) are wanted in the
  modal.**
- **Q5 → H5**: Do real projects contain images with identical basenames in
  different directories (e.g. per-model subfolders)? And do pre-relative-key
  decks (basename alt-text) still circulate and need syncing? **Default: yes
  to both — ambiguity is a real risk and back-compat matters.**
- **Q6 → H6**: Is Python-side testing considered out of scope for this repo
  (covered elsewhere in the fyrverse?) or a known gap worth prioritizing?
  **Default: known gap — weigh it in findings.**
- **Q7**: The metadata sidecar format and `standard_footnotes.yaml` schema are
  described as "mirrors reportifyr". Is there a shared schema definition or
  contract test anywhere, or is it convention maintained by hand? **Default:
  convention only — review for drift accordingly.**
- **Q8 → targeting**: Which matters more for this review: correctness of the
  generated/synced .pptx content, or robustness of the Shiny UI state machine?
  **Default: .pptx content correctness first.**

## 5. Parking lot (noticed in passing, untriaged)

- `R/sync_images.R:38` — `keys_legacy` assigned, never used (dead code;
  relates to H5).
- `inst/scripts/extract_layouts.py:12` — re-defines `USABLE_PLACEHOLDER_TYPES`
  instead of importing from `pptx_utils.py:8` (duplicated constant, drift
  risk).
- `R/server_helpers.R:19` — `regroup_files` breaks if any group has length 0:
  `files[file_idx:(file_idx - 1)]` selects a reversed range (R counts down).
  UI likely can't produce an empty group today, but the function is unguarded.
- `R/pptx_server.R:1024-1028` — `finally = { on.exit({...}) }`: `on.exit`
  registered inside the finally handler fires when the handler frame exits
  immediately; convoluted no-op-ish cleanup.
- `R/pptx_server.R:568-576` — `output$download_synced_pptx` downloadHandler is
  re-registered inside the sync observer on every sync click.
- `R/zzz.R:5-6` — `.onLoad` serves the entire installed package directory as a
  web resource path and sets `shiny.maxRequestSize` (5 GB) globally, affecting
  every Shiny app in the R session.
- `inst/scripts/py_logger.py:23-25` — `get_logger()` clears and re-adds the
  handler on every call; harmless but every module calls it repeatedly.
- `R/pptx_server.R:170-180` and `:1065-1069` — the “append `.pptx` for
  display” logic is duplicated instead of reusing `sanitize_filename`.
- `R/treeNav.R:59-65` — `sapply` over dirs doing `fs::dir_ls` per directory to
  drop empty dirs; O(n) subprocess-ish listing per tree level (perf, minor).
